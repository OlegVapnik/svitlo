# ADR-0009: Private — полный контур, public — срез по allowlist

- **Статус:** Принято (2026-10-27)
- **Дата:** 2026-10-27

## Контекст

Внутренний контур (`cf-worker/`, `tools/`, `tests/`, релизные скрипты, часть `docs/`) скрыт из
публичного репозитория через `.git/info/exclude`. Это осознанное решение: публичный
`OlegVapnik/svitlo` — витрина, а не место для бэкенда.

Фактическое состояние на 2026-10-27:

- `origin/main` содержит **0** файлов `cf-worker/`;
- текущая ветка `fix/d1-save-slots-herostatus-queue-chips` содержит **ровно один** файл
  `cf-worker/src/index.ts` (356 КБ), который импортирует 20 модулей, отсутствующих в публичном
  дереве, — публичная ветка не собирается;
- 8 долгоживущих ветвей (`main`, `internal`, `internal-state`, `public-clean`,
  `public-release`, `redesign-obsidian`, `feat/mascot-settings`, `fix/...`);
- приватный репозиторий `svitlo-internal` создан, но одним orphan-коммитом — без истории,
  ревью и возможности отката;
- любая команда `git add -f` может опубликовать внутренний файл.

Итог: граница приватного и публичного существует, но **не enforced** и уже нарушена частично.

## Решение

1. **`svitlo-internal` (private) — источник истины** для полного контура: `apps/`, `packages/`,
   `cf-worker/`, `tools/`, `tests/`, `docs/`, релизные скрипты, конфиги. С настоящей историей
   коммитов, а не orphan-снимком.
2. **Публичный `OlegVapnik/svitlo` — генерируемый срез** по allowlist:
   `apps/web`, `apps/mobile` (без секретов и внутренних конфигов), `packages/`, `ota/`,
   публичные `docs/`, README, CHANGELOG.
3. Синхронизация — только скриптом `tools/sync-public.sh`:
   - собирает дерево по allowlist в отдельный каталог (или `--dry-run` показывает состав);
   - проверяет, что в срез не попали запрещённые пути;
   - `--publish` клонирует публичный `main`, накладывает срез поверх (витринные
     `apps/`, скриншоты и прочие файлы вне allowlist остаются), проверяет список
     добавленных файлов и пушит fast-forward без force.
   Ручной `git add -f` внутренних путей запрещён.
4. Политика ветвей: `main` + короткоживущие feature-ветки. Долгоживущий `internal` не нужен:
   внутренний контур живёт в отдельном репозитории, а не в ветке публичного.
5. Pre-push hook / CI-проверка: путь из `.git/info/exclude` не может быть в индексе публичного
   репозитория.
6. Релизные теги (`vX.Y.Z`) ставятся в обоих репозиториях на один и тот же код.

## Последствия

**Положительные**

- У внутреннего контура появляются история, ревью и откат.
- Публичная ветка всегда собирается — витрина перестаёт быть «сломанной».
- Риск случайной публикации внутреннего кода падает до машинной проверки.

**Отрицательные / риски**

- Появляется шаг синхронизации; при ручном вмешательстве возможны расхождения.
- Нужно поддерживать allowlist и следить, чтобы публичные клиенты не зависели от
  внутренних пакетов.
- Приватный репозиторий требует дисциплины: туда тоже нельзя коммитить секреты.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Один публичный репозиторий | публикует внутренний контур и секреты |
| Приватная ветка в публичном репозитории | GitHub отдаёт все ветки — приватности нет |
| Git submodule для внутреннего контура | сложная синхронизация и болезненные обновления |
| Хранить внутренний код только локально | нет бэкапа, истории и bus factor = 1 |

## Критерии приёмки

- [x] `svitlo-internal` содержит полное дерево и историю коммитов.
- [ ] Публичный репозиторий собирается из чистого клона.
- [x] Ни один файл из внутреннего контура не отслеживается в публичном.
- [x] Синхронизация выполняется скриптом, а не вручную.
- [x] В публичном репозитории не больше 3 долгоживущих ветвей.

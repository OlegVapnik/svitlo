# ADR-0008: Enforced границы зависимостей и CI-гейты

- **Статус:** Принято (2026-10-27)
- **Дата:** 2026-10-27

## Контекст

Сейчас качество держится на дисциплине и локальных прогонах:

- нет проверки направления зависимостей: `domain` может импортировать React, клиент — сервер,
  модуль — `index.ts`;
- тесты распределены неравномерно: web ≈218, worker ≈102, api ≈427, **mobile — 0**;
- нет контрактных тестов между Worker, схемами и клиентами;
- CI покрывает только iOS-сборку и ручной `direct-sources`; web/worker/api проверяются локально;
- деплой Worker выполняется с ноутбука (`deploy-cf.sh`).

Для соло-проекта это означает: единственный барьер перед продом — память разработчика.

## Решение

1. **Правила зависимостей** (ADR-0001 §5.4) кодируются в `dependency-cruiser`
   (или `eslint-plugin-boundaries`) и запускаются в CI.
2. Единый pipeline для основного контура:

   | Гейт | Что проверяет |
   |---|---|
   | `typecheck` | все воркспейсы |
   | `test` | unit + integration |
   | `contracts` | ответы Worker соответствуют zod-схемам |
   | `schema` | каждая таблица/колонка из SQL есть в миграциях |
   | `boundaries` | запрещённые импорты |
   | `audit` | `pnpm audit --prod --audit-level=high` |
   | `secrets` | скан staged/PR |
   | `ota` | манифест + подпись |

3. **Красный CI = работа не принята.** Локальный успех не является доказательством.
4. Деплой в прод — из CI после зелёного pipeline; ручной деплой — только аварийный путь,
   с записью в CHANGELOG.
5. Новый код без теста не принимается, если он содержит доменное правило или SQL.
   Исключение — чисто визуальные изменения, для них обязательна визуальная приёмка.
6. Тестовый долг mobile закрывается минимальным набором (ADR-0007), а не «когда-нибудь».

## Последствия

**Положительные**

- Архитектурные правила перестают быть пожеланиями.
- Регрессии ловятся до деплоя, а не пользователями.
- Появляется воспроизводимость: CI — единственная точка входа в прод.
- Агенты получают объективный критерий готовности (зелёный прогон), а не «готово».

**Отрицательные / риски**

- Первичная настройка займёт время; часть тестов придётся починить.
- CI на Cloudflare-специфику (Workers/D1) требует Miniflare или локального workerd.
- Слишком строгие границы могут мешать легитимным исключениям — нужен механизм
  задокументированных override.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Полагаться на ревью | ревью нет: один разработчик |
| Только `tsc` | не проверяет слои, контракты и схему |
| Nx/Turborepo с генераторами | лишняя сложность; pnpm-воркспейсов достаточно |
| Запускать проверки вручную перед релизом | уже пропускается под давлением сроков |

## Критерии приёмки

- [x] CI запускается на каждый push/PR и содержит все гейты из таблицы.
- [x] Нарушение правил зависимостей валит сборку с внятным сообщением.
- [ ] Есть тест «ответ соответствует контракту» для каждого публичного эндпоинта.
- [x] Есть тест «схема кода = схема миграций» на чистой базе.
- [ ] Прод-деплой невозможен без зелёного pipeline (кроме документированного аварийного пути).

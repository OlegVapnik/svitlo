# ADR-0007: Клиенты — feature-модули, общая логика, осознанные UI-форки

- **Статус:** Принято (2026-10-27)
- **Дата:** 2026-10-27

## Контекст

Два клиента: `apps/web` (14 613 строк, 149 файлов) и `apps/mobile` (11 087 строк, 61 файл).
Общая логика уже вынесена в `@svitlo/core` (118 импортов) и `@svitlo/shared` (114 импортов) —
это сильная сторона.

Но:

- структура обоих приложений — техническая (`components/`, `pages/`, `hooks/`, `lib/`), а не по
  фичам; изменения одной функции («поиск адреса», «монитор») размазаны по десяткам файлов;
- 8 одноимённых компонентов продублированы между web и mobile (`HeroStatus`, `Timeline24h`,
  `RegionPicker`, `QueueScheduleBar`, `GroupMatrix`, `StatusPill`, `PlaceIcon`, `WavyProgressBar`);
- в `apps/mobile` **ноль тестов**; гейт — `tsc --noEmit` и визуальная приёмка;
- офлайн-состояния обрабатываются в разных местах по-разному.

## Решение

1. Оба клиента организуются **по фичам**:
   `features/home`, `features/monitor`, `features/search`, `features/news`, `features/settings`.
   Внутри фичи — свои `components/`, `hooks/`, `model/`, `api/`.
2. **Логика — общая.** Расчёты, запросы, офлайн, хранение живут в `packages/domain` и
   `packages/client-core`. В фиче остаётся только композиция и представление.
3. UI-форк между web и mobile **разрешён**, когда различие RN/DOM реально (нативная навигация,
   виджеты, шторка уведомлений). Каждый форк обязан:
   - иметь комментарий «почему не общий»;
   - не содержать собственных доменных расчётов;
   - ссылаться на общий тест/фикстуру поведения.
4. Офлайн-состояния — единый набор: `fresh`, `stale`, `offline`, `no-data`, `unavailable`.
   Их различает `client-core`, а не каждый экран.
5. Минимальные тесты mobile: доменные хуки, парсеры, критичные преобразования данных.
   Визуальная приёмка остаётся, но не заменяет тесты.
6. Общие визуальные токены (цвета, отступы, типографика) — единый источник; реализация
   токенов платформенная (CSS variables / NativeWind).

## Последствия

**Положительные**

- Правка фичи локализована; агенты могут работать параллельно по разным фичам.
- Уменьшается число «забытых форков» логики.
- Новый экран добавляется по шаблону, а не изобретается.
- Появляется минимальная страховка для mobile.

**Отрицательные / риски**

- Перекладывание файлов — большой, но механический diff; делать по одной фиче.
- Не все дубли стоит объединять: попытка сделать один UI на две платформы ухудшит обе.
- Тесты mobile требуют настройки jest-expo/vitest и моков нативных модулей.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Общий UI-кит для web и RN | React Native Web тянет компромиссы в производительности и нативности |
| Оставить технические папки | фича продолжает расползаться по слоям |
| Полностью раздельные приложения | дублирование домена и контрактов, которое мы как раз убираем |
| Только web, Android как WebView | теряются виджеты, OTA, уведомления — ключевые преимущества |

## Критерии приёмки

- [x] Оба клиента имеют каталог `features/` и хотя бы 3 фичи, перенесённые целиком
      (web и mobile: `features/{home,monitor,search}`; маршруты expo-router остались тонкими реэкспортами).
- [x] Ни один UI-компонент не содержит доменных расчётов (проверяется ревью и grep по импортам).
- [x] Каждый UI-форк имеет комментарий-обоснование.
- [x] В `apps/mobile` есть тесты на доменные парсеры/форматтеры и они в CI (`vitest run`, 9 тестов, `pnpm -r test`).
- [ ] Офлайн-состояния обрабатываются через `client-core`, а не локально в экранах.

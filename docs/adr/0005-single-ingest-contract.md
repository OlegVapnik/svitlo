# ADR-0005: Единый ingest-контракт; запрет прямых записей в D1

- **Статус:** Принято (2026-10-27)
- **Дата:** 2026-10-27

## Контекст

Данные в прод попадают несколькими путями:

1. крон Worker (`*/20`) — зеркало, Telegram, новости, прямые ОСР;
2. `tools/osr_engine` (Python, systemd, каждые 15 минут) — `POST /internal/schedules-ingest`;
3. GitHub Actions (`direct-sources.yml`, ручной запуск) и скрипты `tools/*.py`;
4. прямые SQL-записи в D1 (`tools/sync-directory-to-d1.mjs`, ручные `wrangler d1 execute`).

У путей разные правила нормализации, состояния (`.cache/osr_state.json`), токены и моменты
применения правил. Исторический пример: инвертированные интервалы Telegram исправлены в
Python, но не в Worker; «виток квоты D1» 24.10 возник из-за тяжёлого пути в прогреве кэша.

Нет единой точки, где можно ответить на вопросы: «что считается валидным снимком?»,
«кто последним записал регион?», «почему в D1 эти слоты?».

## Решение

1. **Один контракт публикации** — `POST /internal/schedules-ingest` (и аналогичные для
   новостей/справочников). Схема — в `packages/contracts`, версионируется.
2. **Сборщик не пишет в D1.** Адаптер (Python/Worker/скрипт) делает только:
   получение → парсинг → canonical DTO → публикация по контракту.
3. Все бизнес-правила применяются **в одной точке** — модуле `ingest` (валидация, fingerprint,
   публикация дня, разбиение инвертированных интервалов, quarantine).
4. Снимок атомарен в разрезе `(source, region, date)`: либо применяется целиком, либо
   отклоняется с диагностикой. Частично валидный снимок не публикуется.
5. Идемпотентность: повторная публикация того же fingerprint не пишет строки.
6. Прямые записи в D1 разрешены только для:
   - миграций схемы;
   - админ-операций, явно описанных в ADR/ранбуке;
   - восстановления из бэкапа.
   Во всех остальных случаях — только ingest.
7. Каждая публикация логируется: источник, регион, дата, количество слотов, fingerprint,
   результат (`applied/quarantined`).

## Последствия

**Положительные**

- Одна точка валидации и один набор правил — расхождения исключены архитектурно.
- Появляется аудит: кто и когда записал данные.
- Проще добавлять новые источники: адаптер + DTO, без знания D1.
- Квоты D1 защищаются в одном месте (diff-write, fingerprint).

**Отрицательные / риски**

- Нужно перевести существующие скрипты на контракт; временно поддерживаем два пути.
- Ingest становится критической точкой: его падение блокирует все источники — нужны
  health-check, алерты и graceful degradation.
- Python-адаптеры теряют возможность «быстро поправить в базе» — это осознанно.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Разрешить прямые записи с ревью | ревью нет; расхождения уже случались |
| Отдельная очередь (Kafka/SQS) | лишняя инфраструктура для соло-проекта и free tier |
| Хранить сырые payload'ы и считать на чтении | дорого по CPU/квотам D1 |
| Оставить как есть | невозможно объяснить происхождение данных |

## Критерии приёмки

- [x] Все активные сборщики публикуют через ingest-контракт.
- [x] В репозитории нет скриптов, делающих `INSERT/UPDATE` в прод-D1 вне миграций/админ-ранбука.
- [ ] Для каждого источника есть тест DTO → ingest → ожидаемые слоты.
- [ ] Повторная публикация не увеличивает `rows_written`.
- [ ] Невалидный снимок попадает в quarantine с причиной, а не в прод-таблицы.

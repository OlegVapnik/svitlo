# ADR-0001: Модульный монолит с гексагональным ядром

- **Статус:** Принято (2026-10-27)
- **Дата:** 2026-10-27

## Контекст

Svitlo — продукт одного разработчика (с ИИ-агентами) в трёх оболочках: PWA, Android, HTTP API.
Прод работает на Cloudflare Free Tier: Worker + D1 + R2 + Pages. Внешние источники данных
(сайты ОСР, Telegram, зеркала) нестабильны и требуют изоляции.

Фактическое состояние:

- доменные правила реализованы 3–4 раза: `cf-worker`, `apps/api`, `packages/core`,
  Python-движок `tools/osr_engine`;
- точка входа Worker — `cf-worker/src/index.ts`, 6572 строки и 356 КБ: маршруты, крон, кэш, SQL,
  парсинг новостей, расчёты надёжности, адресный поиск, R2;
- `apps/api` — 12 837 строк, 20 таблиц, 18 миграций, ≈427 тестов и **ноль прод-трафика**;
- границы модулей не проверяются автоматически: только `tsc --noEmit`.

## Решение

Строим систему как **модульный монолит**:

1. Единственный деплоймент прод-логики — Cloudflare Worker.
2. Код организуется **по доменным модулям**, а не по техническим папкам:
   `schedule`, `news`, `address`, `reliability`, `ingest`, `admin`.
3. Внутри модуля — гексагональная схема: `routes` (вход) → `service` (правила) → `repo` (I/O);
   зависимости направлены к ядру, а не от него.
4. Доменное ядро вынесено в `packages/domain` и не имеет зависимостей (ADR-0003).
5. Контракты — в `packages/contracts` (ADR-0004).
6. Клиенты — адаптеры над общим ядром и контрактами (ADR-0007).
7. `cf-worker/src/index.ts` сокращается до композиционного корня: маршрутизация, `fetch()`,
   `scheduled()`; ориентир — ≤300 строк.

## Последствия

**Положительные**

- Один рантайм и одна инфраструктура — соответствует ресурсам одного разработчика.
- Правка доменного правила делается в одном месте и доезжает до Worker и обоих клиентов.
- Модуль можно менять и тестировать изолированно, не читая 6,5 тыс. строк.
- Появляется возможность параллелить работу агентов по модулям (worktree + границы).

**Отрицательные / риски**

- Требуется дисциплина и автоматическая проверка границ (ADR-0008), иначе монолит снова
  «расползётся».
- Разделение domain/contracts добавляет пакеты и шаг сборки.
- Переход занимает недели и должен идти постепенно (strangler), а не «большим взрывом».

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Микросервисы | 1 разработчик, free tier, сетевые сбои и распределённые транзакции без выгоды |
| Clean Architecture «по учебнику» (5 слоёв) | церемония, не окупается на 70 тыс. строк соло-проекта |
| Оставить как есть | дешево сейчас, но каждая новая область = +1 копия домена |
| Отдельный BFF на каждый клиент | усиливает уже существующую проблему двух бэкендов |
| DDD с агрегатами и event sourcing | нет инвариантов, которые это окупят; усложнит восстановление данных |

## Критерии приёмки

- [x] `cf-worker/src/index.ts` ≤300 строк, без SQL и бизнес-правил.
- [ ] Каждый доменный модуль имеет `routes/service/repo` и собственные тесты.
- [x] Ни одно доменное правило не реализовано дважды (проверяется ревью и тестами-fixtures).
- [x] Правила зависимостей проверяются в CI (ADR-0008).

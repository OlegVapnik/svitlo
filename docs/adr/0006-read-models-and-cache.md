# ADR-0006: D1 — истина, R2 и статика — производные read-модели

- **Статус:** Принято (2026-10-27)
- **Дата:** 2026-10-27

## Контекст

Одни и те же данные доставляются тремя способами:

1. API Worker → D1 (с кэшем в памяти изолята и Cache API);
2. R2-снапшоты: `snapshots/live-state.json`, `/sync`, `/news`;
3. статические паки в `apps/web/public/data` (адреса — 23 МБ, `schedules-all.json`).

Из-за Free Tier D1 (5 млн `rows_read`/сутки) кэш — не оптимизация, а условие работы. Но
текущая схема порождает проблемы:

- неясно, какой источник «свежее» в конкретный момент;
- hot snapshot пишется read-modify-write без версии — известна редкая гонка lost-update;
- флаги деградации (`d1UnavailableAt`, `d1QuotaExceededAt`) — модульные глобалы без сброса:
  после одного сбоя квоты поведение держится до рестарта изолята;
- инцидент 24.10: `/sync` в прогреве читал справочники (24k + 31k строк) на каждый тик,
  ≈833k `rows_read` за 27 минут.

## Решение

1. **D1 — единственный источник истины** для канонических фактов.
2. R2-снапшоты и статические паки — **производные read-модели**:
   - всегда содержат `generated_at`, `source_version` и версию схемы;
   - могут быть удалены и пересобраны без потери данных;
   - никогда не используются для записи обратно в D1.
3. Статические паки **генерируются сборкой** из справочника, а не поддерживаются руками.
   Они — fallback для офлайна/первого запуска, а не основной канал.
4. Каждый ответ API, собранный из производной модели, сообщает происхождение:
   `dataSource`, `generatedAt`, `stale` (если применимо). Клиент различает
   `fresh / stale / offline / no-data`.
5. Запись снапшота — **идемпотентная и версионированная**:
   - сравнение версии (CAS) или запись неизменяемого объекта с ключом, включающим версию;
   - read-modify-write «вслепую» запрещён.
6. Состояние деградации D1 хранится в явной структуре с TTL и сбрасывается по времени,
   а не «до рестарта изолята».
7. Тяжёлые пути (`/sync`) не входят в прогрев кэша и не читают справочники на каждый тик;
   список прогрева — конфигурация с тестом на объём чтения.

## Последствия

**Положительные**

- Понятная иерархия доверия: D1 → снапшот → статика.
- Квоты D1 защищены архитектурно, а не героическими правками.
- Снапшоты можно пересобрать и проверить; нет «второй базы».
- Клиент честно показывает устаревание.

**Отрицательные / риски**

- Нужно добавить метаданные во все снапшоты и научить клиентов их читать.
- CAS/версионирование усложняет запись.
- Генерация статических паков удлиняет сборку web.
- Возможны моменты, когда снапшот отстаёт; UI обязан это показывать, а не скрывать.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Снапшоты как второй источник истины | неизбежные расхождения и ручные синхронизации |
| Только D1 без кэша | превышение free tier и CPU-лимита |
| Только статика | невозможны свежие данные и новости |
| Redis/KV как отдельный кэш | новая инфраструктура и стоимость; Cache API уже есть |

## Критерии приёмки

- [ ] У каждого снапшота и пака есть `generated_at` и версия источника.
- [ ] Нет read-modify-write без проверки версии.
- [ ] Флаги деградации D1 сбрасываются по TTL и покрыты тестом.
- [ ] `/sync` не читает справочники при прогреве; есть тест на объём чтения.
- [ ] Клиент отображает `stale` отдельно от `no-data`.

# Architecture Decision Records (ADR)

Каталог фиксирует **почему** система устроена так, а не иначе. ADR не заменяет
`docs/ARCHITECTURE.md` (там — целостная картина) и не заменяет `PROJECT_MAP.md` (там — снимок
фактического состояния).

## Правила

1. Один ADR — одно решение. Если решение меняется, старый ADR получает статус **Заменено**
   со ссылкой на новый; удалять историю нельзя.
2. ADR пишется **до** реализации, а не после.
3. В ADR обязательны: контекст, решение, последствия (и хорошие, и плохие), альтернативы,
   критерии приёмки.
4. Решение вступает в силу после перевода в **Принято** владельцем проекта.

## Статусы

| Статус | Значение |
|---|---|
| **Предложено** | сформулировано, ждёт решения владельца |
| **Принято** | действует; код и CI должны соответствовать |
| **Заменено** | устарело, есть ссылка на заменяющий ADR |
| **Отклонено** | рассмотрено и не принято; причина сохранена |

## Формат имени

```
NNNN-kebab-case-title.md
```

Номер — следующий свободный, четыре цифры. Заголовок — короткий, про решение, а не про область.

## Шаблон

```markdown
# ADR-NNNN: Название решения

- **Статус:** Предложено
- **Дата:** YYYY-MM-DD

## Контекст
Что вынуждает принять решение. Факты, ограничения, цифры.

## Решение
Что именно решено. Императивно: «делаем так».

## Последствия

**Положительные**
- …

**Отрицательные / риски**
- …

## Альтернативы
| Вариант | Почему не выбран |
|---|---|

## Критерии приёмки
- [ ] проверяемый пункт
```

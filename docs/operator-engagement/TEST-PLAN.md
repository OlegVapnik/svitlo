# TEST-PLAN — план работ в рамках согласованного тестирования

План составлен так, как его сдают по реальному договору: сначала предпосылки, потом объём,
потом явные исключения. Именно отсутствие таких документов (и, тем более, пункта про третьи
стороны) — то, что мешает начать.

## 0. Предпосылки (без них работы не начинаются)

- [ ] разрешение подтверждено письмом **с корпоративной почты оператора** — не с личного адреса;
- [ ] указано окно работ и согласованы IP-адреса, с которых разрешено работать;
- [ ] названо контактное лицо (дежурный) и согласован стоп-сигнал для немедленной остановки;
- [ ] письменно согласовано, что делать с найденными персональными данными (не выгружать,
      не хранить, сообщить немедленно);
- [ ] отдельно урегулирован вопрос третьей стороны: защита Cloudflare. Для проверки антибот-слоя
      владелец включает стенд или тестовые ключи — согласие Cloudflare иначе не получить.

## 1. Цель и результат

Оценить устойчивость публичного контура к автоматизированной нагрузке и качество защиты
персональных данных. **Результат — отчёт, а не инструмент.** Заказчик получает описание проблем и
приоритетов починки.

## 2. Объём работ

1. Инвентаризация публичных эндпоинтов: назначение, какие данные отдаются, какая проверка стоит
   (без атаки — только описание контракта).
2. Проверка наличия серверных лимитов и защиты от перебора — в пределах согласованной интенсивности.
3. Поиск несоразмерности защиты: где барьер стоит на публичных данных, а где персональные данные
   отдаются без проверки (первая находка уже описана в `FINDINGS.md`).
4. Поведение CDN/антибота в штатных и граничных сценариях — описание, без попыток обхода.
5. Отчёт: находки с влиянием и рекомендациями, ограничения, приоритеты.

## 3. Явные исключения (и почему)

- **Обход Turnstile/Cloudflare не входит в работы.** Это защита третьей стороны; вместо обхода
  используется стенд или официальные тестовые ключи, которые включает владелец.
- Любые методы, меняющие состояние системы (POST/PUT/DELETE/PATCH к служебным эндпоинтам).
- Доступ к административному контуру, закрытым базам и инфраструктуре.
- Массовая выгрузка персональных данных, перебор учётных данных, социальная инженерия.
- Нагрузочные сценарии, способные повлиять на доступность сервиса.
- Постоянный сбор данных «в обход»: если нужен регулярный поток данных — оформляется официальный
  доступ или фид, и тогда обход не требуется вовсе.

## 4. Интенсивность и безопасность

- число запросов в секунду — не выше согласованного (предлагается 1–2 с одного адреса);
- немедленная остановка и уведомление дежурного при любой деградации сервиса;
- персональные данные не сохраняются и не публикуются; в отчёте — маскируются;
- все сессии логируются локально для последующей сверки с логами оператора.

## 5. Артефакты

- `FINDINGS.md` — находки (в этом каталоге);
- итоговый отчёт: методика, находки, ограничения, план починки по приоритетам;
- по требованию — акт приёма-сдачи работ.

## 6. Критерий приёмки

- каждая находка содержит наблюдение, описание воспроизведения, влияние и рекомендацию;
- спорные пункты сопровождаются ссылкой на согласованный скоуп;
- ни один пункт работ не выходит за предпосылки из раздела 0.

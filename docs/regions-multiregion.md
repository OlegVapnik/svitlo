# Мультирегіональний ГПВ (Україна) — інструкція оператора

Цей документ описує архітектуру, налаштування та експлуатацію мультирегіонального імпорту графіків погодинних відключень (ГПВ) для операторів системи Svitlo.

---

## 1. Архітектура та джерело даних

API Svitlo розширено з монорегіонального режиму (лише Чернігівська область) на мультирегіональний для областей України.

- **Джерело даних:** публічне «дзеркало» ГПВ (Cloudflare Worker над DTEK-подібним API), налаштоване через `MIRROR_SCHEDULE_URL` (типово `https://dtek-api.svitlo-proxy.workers.dev/`).
- **Один запит на всю Україну:** дзеркало повертає єдиний JSON-payload (~220 КБ), який містить дані для всіх доступних областей одночасно.
- **Цілісний кеш у пам'яті:** отриманий payload кешується цілком у пам'яті процесу на час `MIRROR_SCHEDULE_TTL_SEC` (типово `600` секунд / 10 хвилин). Окремі запити користувачів до різних областей або черг не здійснюють додаткових мережевих запитів до дзеркала.
- **Ідентифікація областей:** регіони адресуються виключно через mirror `cpu` (ідентифікатор у дзеркалі), наприклад:
  - `chernihivska-oblast`
  - `kyivska-oblast`
  - `kyiv-city`
  - `dnipropetrovska-oblast`
  - `odeska-oblast`
  - `lvivska-oblast`
  (Українські назви для інтерфейсу передаються окремим полем `nameUa`).
- **Формат черг:** коди черг у системі Svitlo зберігаються у стандартному форматі застосунку — `1/1`, `2/2` (у дзеркалі ключі груп мають вигляд `1.1`, `2.2` і автоматично конвертуються).
- **Зворотна сумісність:** область за замовчуванням визначається змінною `MIRROR_SCHEDULE_REGION` (типово `chernihivska-oblast`). Якщо клієнт не передає параметр `?region=`, API повертає дані для типової області, тому старі клієнти працюють без змін.

---

## 2. Конфігурація імпорту областей

Змінні середовища в `.env` (та `docker-compose.yml`):

```bash
# Увімкнення дзеркала ГПВ
MIRROR_SCHEDULE_ENABLED=true
MIRROR_SCHEDULE_URL=https://dtek-api.svitlo-proxy.workers.dev/

# Типова область для запитів без ?region=
MIRROR_SCHEDULE_REGION=chernihivska-oblast

# Які області імпортувати в базу даних:
# Порожньо (дефолт) — імпортувати ВСІ області, знайдені у фіді дзеркала.
# Список cpu через кому — звужує імпорт лише до вказаних областей.
MIRROR_SCHEDULE_IMPORT_REGIONS=

# TTL кешу payload у пам'яті (секунди) та таймаут HTTP-запиту (мс)
MIRROR_SCHEDULE_TTL_SEC=600
MIRROR_SCHEDULE_TIMEOUT_MS=15000
```

### Як обмежити імпорт лише окремими областями
Якщо потрібно імпортувати слоти лише для обраних областей (наприклад, для економії місця в БД або фокусу на конкретних регіонах), задайте `MIRROR_SCHEDULE_IMPORT_REGIONS` списком `cpu` через кому:
```bash
MIRROR_SCHEDULE_IMPORT_REGIONS=chernihivska-oblast,kyiv-city,kyivska-oblast
```
Після зміни змінної в `.env` перезапустіть контейнер API:
```bash
docker compose up -d api
```

### Транзакційність запису
Імпорт усіх обраних областей виконується в межах **однієї транзакції БД**. Це запобігає ситуації розсинхронізації («у сусідів графік оновився, а в нас лишився вчорашній»). Спершу очищаються лише власні записи джерела `mirror` за відповідними областями, чергами й датами, після чого слоти додаються через `onConflictDoNothing()`. Ручні та телеграм-записи іншого походження не затираються.

## 3. Перевірка каталогу областей та API

### Перевірка списку областей: `GET /api/v1/regions`
Ендпоінт повертає перелік областей із доступними чергами, кількістю збережених слотів та актуальною датою:

```bash
curl -s localhost:3001/api/v1/regions | head -c 400
```

Приклад структури відповіді:
```json
{
  "data": [
    {
      "cpu": "chernihivska-oblast",
      "nameUa": "Чернігівська область",
      "nameEn": null,
      "queues": ["1/1", "1/2", "2/1", "2/2", "3/1", "3/2", "4/1", "4/2", "5/1", "5/2", "6/1", "6/2"],
      "slots": 96,
      "lastDate": "2026-10-11"
    }
  ]
}
```
Відповідь кешується HTTP-заголовком `Cache-Control: public, max-age=300`.

### Запит графіка з вказівкою області
Ендпоінт `/api/v1/schedules` підтримує параметр `?region=`:
```bash
# Графік для Чернігівської області (черга 2/2):
curl -s "localhost:3001/api/v1/schedules?queue=2/2&region=chernihivska-oblast&date=2026-10-11"

# Графік для Києва:
curl -s "localhost:3001/api/v1/schedules?queue=1/1&region=kyiv-city&date=2026-10-11"
```

### Список черг для області
Ендпоінт `/api/v1/queues` також підтримує параметр `?region=`:
```bash
curl -s "localhost:3001/api/v1/queues?region=chernihivska-oblast"
```

### Канонічні назви областей і псевдоніми `cpu`
Каталог (`packages/shared/src/regions-catalog.ts`) розділяє дві речі, які раніше змішувались:

- **канонічний `cpu` області** — те, що людина бачить у каталозі (`kyivska-oblast`, `kyiv-city`,
  `dnipropetrovska-oblast`);
- **ключ фіда** (поле `feedKeys`) — те, під чим реально лежать дані (`schedule_slots.region`):
  `kiivska-oblast`, `kyiv`, `dnipro-cek`, `dnipro-dnem`.

Правила читання:

1. **Область з одним ключем** підставляється прозоро: `?region=kyivska-oblast` читає
   `kiivska-oblast`, `?region=kyiv-city` — `kyiv`. Підміна нічого не втрачає: це та сама область
   під назвою фіда, і саме заради неї людина не бачила свій графік.
2. **Область із кількома мережами** (м. Дніпро обслуговують ЦЕК і ДнЕМ — різні оператори
   розподільчих мереж із власною нумерацією черг `1/1…6/2`) **не зводиться в один графік**:
   об'єднання інтервалів показало б години відключень, яких у людини немає. Тому каталог віддає
   таку область як **групу** (`feedKeys` довжиною > 1) із підобластями (`parentCpu`), а графік
   вимагає конкретної мережі:
   - `/api/v1/schedules?region=dnipropetrovska-oblast&queue=…` звужується сам, якщо на цю чергу й
     дату дані є лише в одній мережі;
   - якщо дані є в обох — **400 `AMBIGUOUS_REGION`** із переліком ключів, а не злитий розклад;
   - `/api/v1/queues` (це перелік кодів груп, метадані, а не години) лишає канонічний `cpu` і
     зводить коди з усіх мереж;
   - `/api/v1/reliability`, `/api/v1/schedules/upcoming`, `/api/v1/sync` теж вимагають конкретної
     мережі: в інтерфейсі група не обирається — обирається мережа.
3. **Область, якої фід не віддає** (`odeska-oblast`, `sumska-oblast`, …), у каталозі Є, але з
   порожнім `feedKeys` і нулями: людина знаходить свою область і бачить чесне «даних немає», а не
   порожній список без неї.
4. **Друкарський псевдонім** `dnipropetrovnska-oblast` (без `е`) приводиться до
   `dnipropetrovska-oblast`, щоб стара закладка не виглядала як «невідома область».

Приклад перевірки:

```bash
# Київська область: канонічна назва → ключ фіда kiivska-oblast
curl -s "localhost:3001/api/v1/schedules?queue=4/1&region=kyivska-oblast&date=$(TZ=Europe/Kyiv date +%F)"

# Дніпропетровська: 400 з причинами, якщо черга є в обох мережах (ЦЕК і ДнЕМ)
curl -s "localhost:3001/api/v1/schedules?queue=1/1&region=dnipropetrovska-oblast&date=$(TZ=Europe/Kyiv date +%F)"

# Конкретна мережа — працює як звичайна область
curl -s "localhost:3001/api/v1/queues?region=dnipro-cek"
```

Клієнтам, які будують список областей, рекомендується показувати область із `feedKeys.length > 1`
як заголовок групи з підобластями (`parentCpu`) і передавати в `?region=` `cpu` конкретної мережі.
Старі клієнти ці поля просто ігнорують — зворотна сумісність збережена.

### Те саме в Cloudflare-воркері
`cf-worker/src/index.ts` (другий бекенд тієї ж збірки — `./deploy-cf.sh` кладе фронт у Pages, а
запити йдуть на воркер) тримає **копію** каталогу, а не імпорт: воркер збирається wrangler'ом
окремо й навмисно не тягне `@svitlo/shared`. Тому правила треба правити в обох місцях:
`/regions` віддає ту саму структуру з `feedKeys`/`parentCpu` і групою для м. Дніпро, `/queues`
об'єднує коди груп мереж («світло за графіком» — тільки зі згоди кожної), а маршрути однієї мережі
(`/schedules`, `/schedules/upcoming`, `/status`, `/reliability`, `/sync`, `/addresses/*`) на
канонічну область із кількома мережами відповідають 400 `AMBIGUOUS_REGION`.

## 4. Принцип чесного порожнього графіка (No Fake Data)

Відповідно до правила безпеки та цілісності даних Svitlo (Hard Stop #14):
- **Синтетичні графіки заборонені:** якщо за вказаною областю, чергою або датою у фіді немає даних (або передано неіснуючу область) — API повертає **чесний порожній графік**:
  ```json
  {
    "data": {
      "queue": "2/2",
      "date": "2026-10-11",
      "intervals": [],
      "source": null,
      "lastImportedAt": null
    }
  }
  ```
- Запит до невідомої області **не повертає 400 чи 500**, а повертає порожній список інтервалів (так само, як невідома черга).
- Виняток — дві помилки у самому параметрі: сміття замість `cpu` (`?region=xyz--bad`) і область, яку
  фід віддає кількома мережами без конкретної (`?region=dnipropetrovska-oblast`). Перше — 400
  `VALIDATION_ERROR`, друге — 400 `AMBIGUOUS_REGION` із переліком ключів: підставити «щось» означало
  б або вигадати область, або показати чужий графік (див. розділ 3).
- Створювати або симулювати фальшиві відключення суворо заборонено: відсутність світла на графіку повинна відповідати виключно офіційним опублікованим слотам.

## 5. Поведінка при збої або недоступності дзеркала

Система спроєктована з високою відмовостійкістю:

1. **Backoff при збоях (30 с):**
   Якщо мережевий запит до дзеркала завершується помилкою (таймаут, DNS-збій, 5xx), вмикається пауза повторних спроб `MIRROR_FAILURE_BACKOFF_MS = 30000` (30 секунд). Це запобігає зависанню клієнтських запитів на очікуванні та надмірному навантаженню на зовнішній сервіс.
2. **Віддача збереженого знімка (Stale-while-revalidate):**
   Якщо дзеркало недоступне, але в пам'яті процесу є попередній кешований знімок (навіть із простроченим TTL), API негайно віддає його. Відповідь клієнту не падає.
3. **Збережені слоти в БД не видаляються:**
   Усі раніше імпортовані слоти в таблиці `schedule_slots` залишаються цілими. Падіння дзеркала ніколи не призводить до очищення бази.
4. **Порожній каталог замість 500:**
   Якщо дзеркало недоступне і в БД ще немає каталогу, `GET /api/v1/regions` повертає `{ "data": [] }`, а не HTTP 500.

### Дії оператора при аварії дзеркала:
- Перевірити доступність worker зовні:
  ```bash
  curl -sI https://dtek-api.svitlo-proxy.workers.dev/
  ```
- Перевірити логи API-сервісу:
  ```bash
  docker compose logs --tail=100 api | grep -i mirror
  ```
- Примусово запустити повторний імпорт після відновлення джерела:
  ```bash
  curl -s -X POST -H "Authorization: Bearer ${ADMIN_TOKEN}" "http://localhost:3001/api/v1/admin/schedules/import-mirror?force=true"
  ```
- Якщо дзеркало вимкнено або заблоковано на тривалий час:
  Встановіть `MIRROR_SCHEDULE_ENABLED=false` у `.env` та виконайте `docker compose up -d api`. Система повернеться до ручного та Telegram-імпорту графіків.

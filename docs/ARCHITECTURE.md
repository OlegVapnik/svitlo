## 1. Что такое Svitlo с точки зрения архитектуры

Один продукт в трёх оболочках:

| Оболочка | Код | Роль |
|---|---|---|
| PWA | `apps/web` | офлайн-первый клиент, основной веб-вход |
| Android | `apps/mobile` (Expo/RN + Kotlin) | офлайн-первый клиент, OTA, виджеты, уведомления |
| API | `cf-worker` | единственная точка прод-данных: чтение, ingest, крон, раздача APK |
| Эталон | `apps/api` | исторический бэкенд и «оракул» контрактов, вне прода |
| Ядро | `packages/shared`, `packages/core` | контракты и клиентская логика |
| Сбор | `tools/` (Python + Node) | парсеры ОСР, справочники, сборка APK/OTA |

**Главный продуктовый инвариант:** нет данных — нет графика. Состояния «немає даних»,
«застарілий графік» и «світло за графіком» различаются явно на уровне API и UI.

## 2. Драйверы архитектуры

Решения ниже выводятся из этих ограничений, а не из моды.

| Драйвер | Следствие |
|---|---|
| Один разработчик + ИИ-агенты | нельзя содержать две инфраструктуры и три конвейера; правила проверяет машина |
| Cloudflare Free Tier (D1: 5 млн `rows_read`/сутки) | дешёвое чтение, снапшоты, кэш, diff-write |
| Внешние источники нестабильны (WAF, кабинеты, картинки) | каждый источник — изолированный адаптер; домен о них не знает |
| Офлайн и блэкауты | «толстый» клиент, локальное хранилище, статические паки |
| Два клиента (web/RN) | общая **логика**, но не общая разметка |
| Нет команды и ревью | CI-гейты вместо дисциплины; контракты вместо договорённостей |

## 3. As-is: как устроено сейчас

### 3.1. Тип архитектуры

> **Распределённый модульный монолит** с «толстым» офлайн-клиентом, одним прод-рантаймом-комбайном
> (Cloudflare Worker), дублирующим эталонным бэкендом (Fastify/PostgreSQL) и несколькими
> независимыми конвейерами сбора данных.

Это не микросервисы и не Clean Architecture: границы проведены **по рантаймам**, а не по домену.
Внутри Worker есть осмысленные модули (`mirror-sync`, `osr-direct`, `hot-snapshot`, `d1-write`),
но точка входа их не разделяет.

### 3.2. Компоненты и реальные зависимости

```
apps/web ──┐
           ├─→ @svitlo/core ─→ @svitlo/shared (zod)
apps/mobile┘        │
                    └─→ HTTPS ─→ cf-worker ─→ D1
                                     │  ├─→ Cache API
                                     │  ├─→ R2 (снапшоты + APK)
                                     │  └─→ Telegram / RSS / ОСР
tools/osr_engine (Python, systemd) ──┘ POST /internal/schedules-ingest
tools/*.py|*.mjs ────────────────────→ D1 напрямую (SQL) / справочники
apps/api (Fastify) ──────────────────→ PostgreSQL 16 (параллельно, не в проде)
apps/web/public/data ────────────────→ статические паки (23 МБ адресов) в обход API
```

Наблюдения:

- `cf-worker` **не импортирует** `@svitlo/shared` (тот тянет zod и сломал бы бандл): контракты
  описаны типами вручную. Каталог регионов — исключение: `cf-worker/src/regions.ts` теперь
  **генерируется** из `packages/shared/src/regions-catalog.ts` (`pnpm gen:regions`), дрейф
  валит CI.
- `apps/api` умеет то, что в Worker — осознанно пустая форма (`/street-queues`,
  `/places/:account`): решения зафиксированы в `apps/api/README.md` (ADR-0002).

### 3.3. Факты и метрики (на 2026-10-27; исторический срез — до миграции, см. §12 для текущих)

| Метрика | Значение |
|---|---|
| Воркспейсы | 5 в pnpm + отдельный `cf-worker` |
| Код TS/Python | ≈72 тыс. строк; Kotlin — ≈1,25 тыс. |
| Крупнейший файл | `cf-worker/src/index.ts` — **6572 строки / 356 КБ** |
| Маршруты Worker | 26 путей в одном файле |
| Таблицы | D1 — 10; PostgreSQL — 20 (18 миграций) |
| Тесты | web ≈218 / 28 файлов; worker ≈102 / 15; api ≈427 / 43; **mobile — 0** |
| Ветви | 8 долгоживущих (`main`, `internal`, `internal-state`, `public-clean`, `public-release`, `redesign-obsidian`, `feat/mascot-settings`, `fix/...`) |
| Публичный срез | `origin/main`: 0 файлов `cf-worker/`; ветка `fix/...`: ровно 1 файл `index.ts` |

### 3.4. Потоки данных сейчас

1. **Сбор:** крон Worker (`*/20`) + `tools/osr_engine` (systemd, 15 мин) + GitHub Actions +
   ручные скрипты. Три разных набора правил нормализации.
2. **Хранение:** D1 — канонические слоты, покрытие, новости, `outage_events`, справочники.
3. **Чтение:** память изолята → Cache API → R2 hot snapshot → D1.
4. **Доставка клиентам:** API, `/sync`-пакет, статические паки, локальный кэш/SQLite.
5. **Обновления:** APK из R2; OTA-манифест с GitHub raw → Pages, подпись Ed25519.

## 5. To-be: целевая архитектура

### 5.1. Формулировка

> **Модульный монолит с гексагональным ядром (ports & adapters), контрактами как единственным
> источником истины и CQRS-lite на чтении. Один прод-рантайм — Worker. Клиенты — адаптеры.**

Почему так — ADR-0001. Почему не микросервисы, не «Clean Architecture по учебнику», не второй
BFF и не DDD с event sourcing — там же, в разделе «Альтернативы».

### 5.2. Структура

```
packages/
  domain/            # ноль зависимостей; чистая логика
    regions/ queues/ intervals/ publication/ reliability/ addresses/
  contracts/         # zod-схемы, типы, golden fixtures
  client-core/       # React Query, офлайн-кэш, порты storage (эволюция @svitlo/core)

apps/
  web/src/features/*      # фичи: home, monitor, search, news, settings
  mobile/src/features/*   # те же фичи, нативный UI
  api/                    # заморожен как oracle (ADR-0002)

cf-worker/src/
  index.ts                # ~150 строк: fetch() + scheduled()
  modules/
    schedule/{routes,service,repo,ports}.ts
    news/ address/ reliability/ ingest/ admin/
  platform/{d1,cache,r2,snapshots,observability}.ts

tools/
  ingest/                 # транспорт + парсинг → canonical DTO, без бизнес-правил
  release/                # сборка APK/OTA, версии, публикация
```

Переименование `@svitlo/core → @svitlo/client-core` и `shared → contracts + domain` —
опционально и делается на шаге миграции 2; важно разделение ответственности, а не имена.

### 5.3. Доменные модули

| Модуль | Ответственность | Не знает про |
|---|---|---|
| `regions` | каталог 24+1, `feedKeys`, алиасы зеркал, `exempt`-регионы | HTTP, D1 |
| `schedule` | слоты, интервалы, очереди `1/1…6/2`, киевские сутки/DST | источники данных |
| `publication` | «день опубликован», `no_data`, устаревание | транспорт |
| `address` | нормализация, иерархия НП→улица→дом, матчинг очереди | способы хранения |
| `reliability` | окна, минуты без света, агрегаты | UI |
| `news` | категории, регион, дедуп, TTL | канал доставки |
| `outages` | канонические события, статусы `active/scheduled/finished` | парсеры |
| `ingest` | валидация снимка, fingerprint, публикация | источник |
| `release` | версия, OTA-манифест, подпись | клиенты |

Правило: **доменный модуль — чистые функции и типы**. I/O живёт в адаптерах
(`platform/*` в Worker, `api/*` в клиентах, `transport/*` в Python).

### 5.4. Правила зависимостей

```
domain ← contracts ← client-core ← apps/*
   ↑
   └──────────── cf-worker/modules ← platform
```

| Разрешено | Запрещено |
|---|---|
| `domain` → ничего (кроме стандартной библиотеки) | `domain` → zod/fetch/D1/React |
| `contracts` → `domain` (типы) | `contracts` → клиенты |
| `cf-worker/modules/*` → `domain`, `contracts`, `platform` | модуль → `index.ts` |
| `apps/*` → `client-core`, `contracts`, `domain` | `apps/web` → `apps/mobile` |
| `platform` → D1/R2/Cache API | `platform` → бизнес-правила |

Проверяется автоматически: `dependency-cruiser` (или `eslint-plugin-boundaries`) в CI, см. ADR-0008.

### 5.5. Жизненный цикл запроса (целевой)

```
GET /api/v1/schedules
  → index.ts (роутинг) → modules/schedule/routes.ts
  → service.ts (правила из domain)
  → repo.ts (SQL к D1) → platform/cache.ts (дешёвое повторное чтение)
  → JSON, провалидированный схемой contracts
```

`index.ts` не содержит SQL, парсинга, расчётов и HTML.

## 6. Данные

### 6.1. Классификация

| Класс | Примеры | Источник истины | Производные |
|---|---|---|---|
| Канонические факты | `schedule_slots`, `schedule_coverage`, `outage_events`, `news` | D1 | R2-снапшоты, `/sync` |
| Справочники | НП, улицы, дома, `address_queues` | D1 + генерируемые паки | `public/data/address` |
| Служебное | `snapshot_meta`, health, версии | D1 / R2 | кэш ответов |
| Персональное | закладки, настройки | устройство пользователя | — |

**Правило:** у каждого факта ровно один владелец. Производные можно удалить и пересобрать;
канонические — нельзя.

### 6.2. Ingest

Один контракт публикации (`POST /internal/schedules-ingest`) и одна точка применения правил.

```
источник → адаптер (парсинг/транспорт) → canonical DTO → ingest (валидация, fingerprint)
        → D1 (diff-write) → инвалидация кэша → R2 read model
```

Запрещено: писать в D1 напрямую из скриптов, кроме явных миграций/админ-операций,
задокументированных в ADR-0005. Источник не может публиковать «частично валидный» снимок.

### 6.3. Чтение и кэш

Приоритет и правила:

| Уровень | TTL | Роль |
|---|---|---|
| Память изолята | 2–5 мин | защита CPU |
| Cache API | минуты | переживает изолят |
| R2 snapshot | до пересборки кроном | read model для «тяжёлых» ответов (`/sync`, `/news`) |
| D1 | — | истина |

Правила:

- Снапшот — **производное**, а не второй источник истины: он всегда помечен временем сборки.
- Запись снапшота идемпотентна; read-modify-write без версии запрещён (известная гонка
  hot-snapshot должна уйти вместе с рефакторингом `platform/snapshots`).
- Флаги деградации D1 (`d1UnavailableAt` и подобные) живут в явном состоянии с TTL, а не в
  модульных глобалах.
- Клиент не считает статический пак свежее API: в ответе есть признак происхождения/возраста.

### 6.4. Схема и миграции

- Единственный источник схемы прод-БД — версионируемые миграции; `schema.sql` — их свёртка
  для чистой установки.
- `ensureSchema()` не расширяется вручную: только идемпотентные миграции.
- Тест «каждая таблица/колонка, упомянутая в SQL кода, существует в схеме» — обязателен
  (исторически `address_queues` отсутствовала в `schema.sql`).
- Судьба PostgreSQL-схемы — ADR-0002.

## 7. Контракты и совместимость

- `packages/contracts` — единственный источник схем запросов/ответов (zod).
- Worker валидирует исходящие ответы в тестах и на границе ingest — не «на глаз».
- Изменение контракта: сначала схема + fixture, потом реализация; ломающие изменения — новая
  версия поля/эндпоинта, а не тихая замена.
- Заглушки запрещены: если функция недоступна в среде, ответ содержит явный признак
  (`available: false` / `source: "unavailable"`), а не пустой массив, неотличимый от «нет данных».
- OpenAPI/типы для внешних потребителей генерируются из схем, а не пишутся руками.

## 8. Клиенты

- **Общее:** домен, контракты, React Query-хуки, офлайн-кэш, порты хранилища.
- **Раздельное:** разметка и нативные возможности (виджеты, уведомления, OTA).
- UI-дубли (`HeroStatus`, `Timeline24h`, `RegionPicker` и др.) допустимы **только** там, где
  различие RN/DOM реально; логика внутри них обязана быть общей. Каждый форк фиксируется
  комментарием «почему не общий».
- Офлайн: единственный путь чтения — через `client-core`, с явными состояниями
  `fresh / stale / offline / no-data`.
- Мобильные тесты: минимум на доменные хуки и парсеры; визуальная приёмка — не замена тестам.

## 9. Качество и CI

Обязательные гейты на каждый PR/коммит в основной контур:

| Гейт | Команда (ориентир) |
|---|---|
| Типы | `tsc --noEmit` во всех воркспейсах |
| Unit/integration | `pnpm -r test`, `cd cf-worker && node --test tests/*.test.ts` |
| Контракты | тест ответов Worker против `packages/contracts` |
| Схема | проверка «код ↔ миграции» на чистой D1/SQLite |
| Границы | `dependency-cruiser` по правилам §5.4 |
| Зависимости | `pnpm audit --prod --audit-level=high` |
| Секреты | secret scan на staged/PR |
| OTA | `tools/verify-ota-manifest.mjs` + проверка подписи |

Правило: **красный CI = работа не принята**. Локальный «у меня работает» не является гейтом.

## 10. Эксплуатация

- **Окружения:** prod (Cloudflare) + локальный стенд. Staging D1 — открытый вопрос (§13).
- **Деплой:** только из CI, с проверкой версии и smoke-запросами (`/health`, `/version`,
  `/regions`). Ручной `deploy-cf.sh` — аварийный путь, а не норма.
- **Секреты:** менеджер паролей/CI secrets; `.env` — только локально, `0600`. Ротация после
  любой подозрительной утечки.
- **Релизы:** одна версия — один источник (ADR-0010); OTA-манифест и APK проверяются скриптом.
- **Наблюдаемость:** health/статус источников, лог шагов крона, счётчики `rows_read` по
  тяжёлым путям. Ошибка одного источника не должна ронять остальные.
- **Репозитории:** private — полный контур и история; public — срез по allowlist (ADR-0009).

## 11. Миграция без переписывания

Принцип: **strangler** — каждый шаг самостоятельно деплоится и оставляет тесты зелёными.

| Шаг | Действие | Критерий готовности | Статус (2026-10-28) |
|---|---|---|---|
| 0 | Зафиксировать этот документ и ADR; включить CI-гейты; один рабочий ствол | CI краснеет на типах/тестах; правило «1 источник правды» записано | ✅ CI с typecheck, тестами, дрейфом регионов, границами зависимостей (ADR-0008) |
| 1 | Генерировать `cf-worker/src/regions.ts` из общего каталога; контрактные тесты Worker ↔ `contracts` | нет ручных копий каталога и контрактов | ✅ каталог генерируется (`pnpm gen:regions`, гейт на дрейф); `packages/contracts` ещё не выделен — зодиак-схемы в `@svitlo/shared` |
| 2 | Вынести домен в `packages/domain` по одному модулю (регионы → интервалы → публикация → адрес → надёжность) | Worker и клиенты импортируют один код; тесты переехали | ✅ 10 модулей, 79 тестов; core/cf-worker реэкспортируют |
| 3 | Разрезать `index.ts` по модулям без изменения поведения | файл ≤300 строк; маршруты разложены; тесты те же | ✅ `index.ts` 6572 → 170 строк; 10 модулей + 11 файлов платформы; 99 → 107 тестов |
| 4 | Решить судьбу `apps/api` (заморозка или удаление с переносом тестов) | нет второй живой правды | ✅ заморожен как oracle (ADR-0002), поверхность маршрутов под тестом |

## 13. Открытые вопросы

1. **Staging D1**: нужен ли отдельный экземпляр для проверки миграций, или достаточно
   локального SQLite/Miniflare?
2. ~~**Судьба `apps/api`**~~ — решено: заморозка как oracle (ADR-0002), поверхность
   маршрутов зафиксирована тестом `apps/api/tests/frozen-surface.test.ts`.
3. **Python vs Worker ingest**: оставить оба транспорта при одном контракте или свести к одному.
4. ~~**Мобильные тесты**~~ — решено: vitest для чистых модулей (`apps/mobile/tests`, 9 тестов, гейт `pnpm -r test`); нативные модули по-прежнему покрывает визуальная приёмка.
5. **iOS**: считается ли отдельной целью поддержки и какие гейты к ней применяются.
6. ~~**Публичный срез**~~ — решено: `tools/sync-public.sh` собирает срез по allowlist, а `--publish` наложением обновляет `origin/main` (проверка запрещённых путей перед коммитом).

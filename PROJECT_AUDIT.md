часть docs были скрыты из публичного репозитория **намеренно**: это внутренний контур, его

секреты и зависимости.

## Critical

### C-2. OTA обновляет исполняемый JS без криптографической подписи

**Доказательства**
- Манифест и бандл берутся с GitHub raw, затем с Pages (`apps/mobile/src/lib/ota.ts:38-42`).
- Проверяется только `sha256` из того же манифеста (`ota.ts:308-310`).
- Отдельной подписи манифеста/бандла нет; в `OtaBundle.kt` тоже нет проверки публичным ключом.
- Первичный источник — ветка `main` GitHub, содержимое которой можно изменить без релиза APK.

**Влияние**
- Компрометация GitHub-аккаунта, ветки `main` или доверенного канала OTA даёт доставку
  произвольного JS в установленные приложения. SHA-256 не защищает: атакующий меняет и
  бандл, и хэш в манифесте.
- Для приложения это фактически удалённое исполнение кода с доступом к данным пользователя,
  сети и локальному хранилищу.

**Рекомендация**
1. Подписывать манифест Ed25519/ECDSA ключом, публичный ключ зашить в APK.
2. Проверять подпись до скачивания бандла и до распаковки; подпись не должна лежать рядом
   с манифестом в том же изменяемом канале.
3. Перевести primary-источник на неизменяемый артефакт (R2/Pages с релизным тегом или
   GitHub Release), а не на `main`.
4. Хранить приватный ключ вне репозитория; ротировать при компрометации.
5. Добавить тест: подмена байта бандла и подмена манифеста должны отклоняться.

### H-4. Публикация OTA может оставить GitHub-манифест и бандл рассинхронизированными

**Доказательства**
- `tools/publish-ota.sh:25` задаёт `OTA_DIR`, но нигде его не использует.
- `tools/publish-ota.sh:56` деплоит только `apps/web/dist` в Pages.
- Приложение сначала читает `https://raw.githubusercontent.com/.../main/ota`
  (`apps/mobile/src/lib/ota.ts:38`), то есть корневой `ota/`, а не Pages.
- `HANDOFF.md` прямо требует вручную синхронизировать `ota/` в GitHub.

**Влияние**
- Новый APK/OTA-релиз может опубликовать манифест на Pages, но установленные клиенты
  прочитают старый манифест с GitHub.
- Обратная ситуация: обновлённый GitHub-манифест ссылается на отсутствующий/старый бандл.
- Итог — «обновление не приходит», 404, либо откат на вшитый бандл; диагностика сложная.

**Рекомендация**
1. Сделать один источник истины: либо GitHub Release asset, либо R2, либо Pages.
2. Если оставить GitHub raw — `publish-ota.sh` должен атомарно обновлять корневой `ota/`,
   коммитить и пушить, а затем проверять доступность `version.json` и бандла.
3. Добавить smoke-check после публикации: скачать манифест по всем источникам, сверить
   `version`/`sha256`, проверить размер.
4. Удалить неиспользуемый `OTA_DIR` или реализовать его.

### H-5. Внутренний контур скрыт правильно, но не имеет приватной копии и истории

**Это не уязвимость и не ошибка сокрытия.** `cf-worker/`, `tools/`, `tests/`, `wrangler.toml`,
`HANDOFF.md` и часть docs скрыты из публичного `OlegVapnik/svitlo` намеренно. Публичный
репозиторий и должен оставаться витриной без внутреннего бэкенда.

**Доказательства**
- `.git/info/exclude:50-87` скрывает `cf-worker/`, `tools/`, `tests/`, `deploy-cf.sh`,
  `docker-compose.yml`, `.github/`, `cf-worker/wrangler.toml` и др.
- `git ls-files cf-worker` → `0`.
- В `origin/main` есть `apps`, `packages`, `ota`, скриншоты и корневые файлы; нет
  `cf-worker`, `tools`, `tests`.
- Внутренний код существует только в рабочей копии на этой машине: ни приватного remote,
  ни истории коммитов, ни второго экземпляра.

**Влияние**
- Потеря диска/рабочей копии = потеря прод-кода; bus factor = 1.
- Нет истории и code review для самого критичного компонента; нельзя откатиться к
  предыдущей версии Worker/скрипта.
- Нет CI для Worker, схемы D1 и release-скриптов.
- Любая правка `.git/info/exclude` или команда `git add -f` может случайно опубликовать
  внутренний код.

**Важно:** приватная ветка внутри **публичного** GitHub-репозитория не является приватной —
GitHub отдаёт все ветки. Поэтому вариант «ветка `internal` в `OlegVapnik/svitlo`» не решает
задачу. Нужен отдельный **private** репозиторий (или private fork), а публичный — только
чистый срез.

**Рекомендация**
1. Создать отдельный приватный репозиторий, например `svitlo-internal`, с полным деревом:
   `cf-worker/`, `tools/`, `tests/`, `apps/`, `packages/`, docs, `HANDOFF.md`.
2. Убрать внутренние пути из `.git/info/exclude` **в клоне приватного репозитория** (не в
   публичном), закоммитить и включить remote backup.
3. Публичный `OlegVapnik/svitlo` оставить витриной: `apps/web`, `apps/mobile` (без
   внутренних секретов), `packages`, `ota`, публичные docs, README.
4. Написать `tools/sync-public.sh`, который собирает чистый срез по allowlist в отдельный
   каталог/ветку, проверяет отсутствие запрещённых путей и секретов и только затем пушит в
   публичный remote. В публичный репозиторий не должно попадать ничего сверх allowlist.
5. Добавить CI в приватный репозиторий: typecheck, тесты Worker, web, mobile, `pytest`,
   проверка D1-схемы. В публичном — только сборка витрины.
6. Проверить, что публичная история не содержит внутренних файлов и секретов; при
   необходимости почистить историю публичного репозитория.

- Клиенты используют эти маршруты как общие.

**Влияние**
- В проде пользователь видит «нет данных» вместо реальной привязки, хотя Node-API умеет
  это делать.
- Легко принять за баг клиента; контракт формально совпадает, семантика — нет.
- Нет теста, который фиксирует «в Worker это намеренная заглушка».

**Рекомендация**
- Явно задокументировать divergence в `PROJECT_MAP.md` (сделано) и в OpenAPI.
- Добавить заголовок/поле `source: "unavailable"` или отдельный статус, чтобы клиент
  отличал «нет привязки» от «функция недоступна в этой среде».
- Либо перенести данные в D1, либо убрать маршруты из публичного Worker-контракта.

### L-1. CORS `*` в Worker

## Открытый вопрос: виджеты на HyperOS / One UI

Симптом: на устройствах HyperOS/One UI виджеты не работают. В этом проходе не воспроизведено:
`adb devices` пуст, логов с устройства нет. Поэтому ниже — не подтверждённый диагноз, а
проверенные по коду факты и гипотезы.

**Что проверено**
- Три провайдера (`SvitloWidget2x1/4x1/4x2`) объявлены в манифесте с `exported=true`,
  `APPWIDGET_UPDATE` и `meta-data`; `SvitloWidgetPackage` подключён в `MainApplication`.
  Проблема не в отсутствии receiver'а.
- Во всех XML `android:updatePeriodMillis="0"` (`native-android/res/xml/svitlo_widget_*.xml`):
  система **не** будит виджет по расписанию. Снимок пишется только когда жив процесс
  приложения и смонтирован главный экран (`useHomeWidget`), либо при `onUpdate`/ресайзе/ребуте.
- Нет `WorkManager`/`AlarmManager`/headless-задачи для фонового обновления. Если HyperOS/One UI
  убивает процесс, виджет остаётся со старым снимком до следующего открытия приложения.
  Это согласуется с жалобой, но не доказывает её.
- Все исключения в `SvitloWidgetProvider.update()` проглатываются, а при сбое рендера
  показывается fallback «Немає даних». Без логирования невозможно отличить «нет данных»,
  «процесс убит», «Bitmap не создался» и «лаунчер не прислал опции».
- `updatePeriodMillis=0` также означает, что после перезагрузки виджет не обновляет данные
  сам, а только перерисовывает последний снимок из `SharedPreferences`.
- Попутный дефект: `widgetAction()` пишет `pending_action` в момент **создания**
  `PendingIntent`, а не в момент клика (`SvitloWidgetProvider.kt:231`). Поэтому обычный тап по
  телу виджета может позже consumed-нуться как «refresh»/«next_queue». Это не причина
  «виджет не работает», но поведение кликов стоит исправить.

**Что нужно для точного диагноза**
1. Симптом: виджета нет в списке / добавлен пустой / показывает «Немає даних» / показывает
   старые данные / крашится лаунчер.
2. Модель устройства, версия HyperOS/One UI, Android API, сборка APK (2.37.9 release или debug).
3. Логи с подключённого устройства:
   ```bash
   adb shell dumpsys appwidget | rg -C 3 'ua.com.svitlo'
   adb shell pm dump ua.com.svitlo.app | rg -C 3 'SvitloWidget|APPWIDGET'
   adb logcat -c && adb logcat | rg -i 'SvitloWidget|AppWidget|AndroidRuntime'
   ```
4. Проверить, обновляется ли виджет сразу после открытия главного экрана и остаётся ли
   stale после убийства приложения.

**Вероятный порядок проверки**
- Сначала подтвердить, что провайдер виден системе (`dumpsys appwidget`).
- Затем — что `onUpdate` вызывается и `Bitmap` не пустой (добавить логирование вместо
  молчаливого `catch`).
- Потом — что снимок в `SharedPreferences` пишется (сейчас только с главного экрана).
- И только после этого добавлять фоновое обновление (WorkManager/periodic), иначе на
  HyperOS/One UI оно всё равно упрётся в battery optimization.

## 1. Вердикт: говно или нет?

**Нет, не говно. Но и не продакшен.** Это хороший прототип с добротной «чистой» логикой и сломанным фундаментом данных и эксплуатации.

Если коротко:

- **Код предметной логики** (время Киева, интервалы, классификация, надёжность, нормализация) выглядит аккуратно: чистые функции, отдельные файлы, тесты именно на них. Это самая ценная часть, её не надо выбрасывать.
- **Данные** — главная беда. Одно и то же событие считается в четырёх местах по-разному, дедупликация делается «на лету» при чтении, классификация (авария/ремонт) дублируется в бэкенде и фронтенде регулярками по украинскому тексту. Отсюда «30 вместо 6» в статистике.
- **Продукт сейчас фактически не живой**: планировщик выключен (данные обновляются только ручным `POST /admin/parse`), в проде включён `SCHEDULE_DEMO=true` (жителям может показываться выдуманный график), реальные ГПВ не импортированы, контейнеры остановлены.
- **Эксплуатация и безопасность** на уровне «работает на моей машине»: нет git, нет CI, порт БД с дефолтным паролем (роль/база `svitlo`, пароль `energymon`) проброшен наружу, нет HTTPS (а это PWA), админские страницы лежат в публичной навигации.

**Решение: не переписывать с нуля.** Переписать нужно **ядро данных** (модель события + единая точка дедупликации и агрегации) и **эксплуатацию**. Парсеры, функции времени, схемы zod, большую часть UI — оставить и подчистить.

## 2. Что сделано хорошо (это не ломать)

1. **Единая zod-схема конфига** (`config.ts`) — один источник настроек, понятный порядок добавления новой.
2. **Чистая логика вынесена и покрыта тестами**: `power-summary`, `reliability`, `outage-grouping`, `outage-classification`, `schedule-normalizer`, `incident-status`, `address-matcher`.
3. **Дисциплина времени**: всё в UTC в БД, «киевские» сутки — хелперами, DST учтён (`kyivDayStart`). Мало кто делает это правильно.
4. **Идемпотентный upsert** по `content_hash` + `(source, external_id)`, миграции в транзакциях с журналом.
5. **Устойчивость парсинга**: `runParse` не падает целиком при недоступном основном источнике.
6. **Честный флаг `demo:true`** и `dataStale` — идея правильная (проблема в том, что демо включено по умолчанию).
7. **Единый формат ответов/ошибок** (`{data}` / `{error:{code,message,details}}`).
8. **PWA с `NetworkFirst`** для API — для приложения про отключения света это именно то, что нужно: во время отключения связь плохая.
9. **Секреты учтены в `.gitignore`**, есть миграция `0005_remove_seed_personal_data` — вы уже сталкивались с персональными данными и убрали их.
10. **Docker Compose**: `depends_on` с `service_healthy` / `service_completed_successfully`, обязательный `ADMIN_TOKEN`, TLS-цепочка оператора решена через `NODE_EXTRA_CA_CERTS`, а не отключением проверки сертификата.

## 3. P0 — критичное

### 3.1. Продукт не обновляет данные сам [карта]

`ENABLE_SCHEDULER=false` зашито в `x-api-env` и перекрывает `.env`. Данные появляются только по ручному `POST /admin/parse`. Приложение «мониторинг отключений» без автообновления — это статичный сайт, который через 2 часа начинает показывать `dataStale`.

**Что делать:** включить планировщик в проде; оставить выключатель как аварийный (`ENABLE_SCHEDULER`), но по умолчанию `true`. Добавить алерт, если `last_success_at` старше N минут (см. §7.5).

### 3.2. Демо-данные включены в проде [карта]

`SCHEDULE_DEMO=true` «всегда» в compose. Пока `schedule_slots` пуст, жителям отдаётся синтетический график. UI помечает его, но человек, решающий по такому графику, когда включать зарядку/готовить, получает **выдуманную информацию** в приложении про реальное электричество.

**Что делать:** `SCHEDULE_DEMO=false` в прод-конфиге; блок «Мій графік» при отсутствии данных показывает «Графік ще не завантажено» (EmptyState), а не демо. Демо — только в dev-профиле compose (`docker compose --profile demo`).

### 3.3. Порт БД открыт, пароль тривиальный [карта]

Таблица портов: `5432 | PostgreSQL (роль/база `svitlo`, пароль `energymon`, слушает только 127.0.0.1)`. Если это проброшено на `0.0.0.0` на сервере — БД в интернете с паролем `energymon`.

**Что делать:** убрать публикацию порта 5432 (сервисам внутри сети он не нужен), либо `127.0.0.1:5432:5432`; пароль — из `.env`, длинный случайный. **[проверить]** если контейнер где-то уже был доступен снаружи — считать данные скомпрометированными и сменить `ADMIN_TOKEN`.

### 3.4. Нет git [карта]

Репозиторий без `.git`, истории нет, откатиться нельзя. Карта сама это отмечает дважды (§0 и §12.9).

**Что делать сегодня, до любых правок:** `cp -r` в архив → `git init` → проверить `.gitignore` (в частности `.env`, `snapshots/`, `operator-samples/`, `/1/`, `nohup.out`, `.turbo/`) → первый коммит → приватный удалённый репозиторий.

### 3.5. Секреты и персональные данные [карта]

- В `/tmp/*` могут лежать `ADMIN_TOKEN` и **номера лицевых счетов** (§13.9).
- Ответы оператора могут содержать номера счетов и сессии (§12.8).
- В `useMyAddress` при очистке удаляется `myAccountNumber` — значит номер счёта когда-то хранился в `localStorage` у пользователей.
- Миграция `0005` чистит «персональные данные» из сидов.

Номера лицевых счетов — персональные данные. **[проверить]**: (а) сохраняются ли они в `raw_snapshot_ref` / `telegram_posts.raw_snapshot_ref` / каталоге `snapshots/`; (б) попадают ли в `addresses_raw`; (в) остался ли код, пишущий `myAccountNumber`. Удалить `/tmp/*`, сменить `ADMIN_TOKEN`, добавить санитайзер на ингесте (вырезать всё, похожее на номер счёта, до записи в БД и в снапшоты).

### 3.6. Админка в публичном интерфейсе [карта]

`Sidebar` содержит пункты «Імпорт графіка» и `/streets` с админ-формой; `ADMIN_TOKEN` вводится руками в браузере. Это значит:

- любой житель видит админские страницы;
- токен проходит через браузер (расширения, XSS, история, скриншоты, экран при демонстрации);
- один статический токен без ротации, без разделения прав.

**Что делать:** вынести админку в отдельный маршрут, не показываемый в навигации и закрытый на уровне nginx (basic auth / IP allowlist / отдельный поддомен). Лучше: CLI-скрипт/`curl` для импорта вместо UI. Сравнивать токен через `timingSafeEqual` **[проверить]**, отдельный rate-limit на `/admin/*`.

### 3.7. Нет HTTPS при заявленном PWA [вывод]

В compose нет TLS-терминации (Caddy/Traefik/nginx+certbot). Service worker и установка PWA на не-`localhost` работают **только по HTTPS**. То есть вне локальной машины «PWA» либо не регистрируется, либо вы что-то терминируете вне compose — в карте этого нет. **[проверить]** где реально живёт прод.

## 4. P1 — архитектура и модель данных

### 4.1. Дедупликация на чтении вместо записи [карта]

`mergeDuplicateOutages` вызывается в `/outages`, `/incidents`, `/status`, `/reliability`, но **не** в `/outages/stats`. Результат: 30 против 6. Карта говорит «помнить про 4 места» — это не решение, а признание проблемы: инвариант держится на памяти разработчика.

Дополнительно:

- выборка ограничена `MAX_ROWS_FOR_GROUPING=1000` → дедуп → `slice`. **[вывод]** при >1000 строк данные **молча отбрасываются**, и непонятно, какие именно (зависит от `ORDER BY`);
- `meta.total/totalPages` считаются **после** дедупа по усечённой выборке, значит это не настоящая пагинация; в роуте зашито `{page:1, limit:50}`;
- `GET /outages/:id` — какой `id` у «склеенного» события? Деталь покажет одну из склеенных строк, не всё событие.

**Как правильно:** разделить «событие» и «затронутые адреса».

```
outage_events     (id, source_id, external_key UNIQUE, starts_at, ends_at,
                   category, reason, area_name, status_cached, first_seen_at, updated_at)
outage_addresses  (event_id → outage_events.id, address_raw, address_normalized, street_id?)
```

Дедупликация происходит **один раз, на ингесте** (`outageEventKey` уже есть — используйте его как `UNIQUE`-ключ). Тогда `/outages`, `/status`, `/reliability`, `/outages/stats` читают одну таблицу, и расхождение цифр структурно невозможно. Пагинация, фильтры и сортировка — в SQL.

### 4.2. Три пересекающиеся сущности [карта]

Outage / Incident / Schedule — «легко перепутать» (слова карты). При этом:

- `incidents` — **проекция** `outages` (kind `outage`) + сообщения (kind `report`), собираемая на чтении;
- адаптер ещё и **пишет** инциденты из отключений (`emergencyIncidentFromOutage`) — то есть дублирование и на записи;
- `outages.status` пересчитывается `updateOutageStatuses()` при парсинге, а для инцидентов состояние «вычисляется на чтение» (`outageIncidentState`). **Два источника правды о статусе.** При выключенном планировщике сохранённый `status` в БД устаревает, а вычисляемый — нет.

**Решение:** статус — только вычисляемый (из `starts_at/ends_at/now`), столбец `status` оставить только для `cancelled`. Инцидент — это **представление** (view/маппер) события, не отдельная таблица с отдельным `external_id`; отдельной остаётся только сущность «сообщение» (`report`).

### 4.3. Классификация регулярками по тексту [карта]

`isRegimeNotice`, `isOutageIncident`, `isRepairIncident`, `shouldShowIncident` — регулярки по украинскому тексту; на фронте **вторая копия** (`outageCategory` в `lib/outage-location.ts`). Эта дублированная копия уже дала баг: вкладка «Графіки» не показывала ремонт, потому что фронт фильтровал `category === 'incident'`.

**Решение:**
1. Категорию считает только бэкенд, один раз на ингесте, хранит в столбце `category` (`emergency | repair | regime | planned | other`).
2. Фронт получает готовое поле и не содержит регулярок.
3. Регулярки покрыть таблицей реальных строк оператора (golden-файл из снапшотов с вырезанными ПД) — любое изменение формулировок оператора ловится тестом.
4. Неклассифицированное → `other` + лог `warn`, а не молчаливый отсев.

### 4.4. Четыре расчёта «времени без света» [карта + вывод]

`status` (`powerSummary`), `reliability`, `outages/stats` и таймлайн считают независимо. Часть логики интервалов вынесена в `power-summary.ts` (хорошо), но не все её используют.

**Решение:** все агрегаты строить поверх одной функции «слить интервалы событий за окно» (`mergeIntervals` уже есть) и одного источника событий (§4.1). `outages/stats` (теплокарта, по часам, по дням) тоже считать из тех же деdуплицированных событий — либо в SQL по `outage_events`, либо на лету через тот же слой.

### 4.5. Таблица `outages` — «широкая и грязная» [карта]

- `source_id` **и** `source` — два поля про одно;
- `addresses_raw` / `addresses_normalized` — текстовые блобы; адресов много на одно событие, поэтому GiST-trgm по ним и LIKE-fallback в поиске;
- два разных ключа уникальности (`(content_hash, source_id)` и частичный `(source, external_id)`) — две стратегии дедупа в одной таблице;
- `queue` в `outages` — а очередь это понятие графика (`schedule_slots`).

**[проверить]** что значит `queue` в `outages` и откуда берётся — если это тот же «2/2», что в графиках, связь неявная.

### 4.6. Миграции: три источника правды [карта]

- `schema.ts` (Drizzle);
- «сырые» SQL-миграции, написанные вручную;
- `drizzle-kit generate` настроен, но «руками почти не нужен».

Это гарантированный дрейф: изменили схему в `schema.ts` и забыли SQL (или наоборот), TypeScript пройдёт, рантайм упадёт. Кроме того:

- **данные в миграциях** (`0004` — ~20 улиц, `0007` — запись источника) — сиды живут только там и в админ-API: `db/seed.ts` удалён 2026-10-10 (вставлял выдуманные данные); `0005` существует, потому что в сид когда-то попали ПД;
- `energy_normalize_address()` пересоздаётся в `0001`, `0002`, `0004`. Если эта функция участвует в индексе/столбце `name_normalized`, а определение менялось, **старые значения не пересчитаны** → индекс и данные расходятся **[проверить]**;
- функция помечена `IMMUTABLE`, а `unaccent` по умолчанию `STABLE` — обёртка допустима, только если оборачивать явно с указанием словаря, иначе возможны тихие ошибки индексов **[проверить]**;
- идемпотентность через `IF NOT EXISTS` в каждой миграции нужна именно потому, что раннеру не доверяют — признак проблемы.

**Решение:** выбрать одно — либо Drizzle-kit как единственный генератор (`generate` + `migrate`), либо SQL-first с автоматической проверкой соответствия `schema.ts` (CI-шаг: поднять БД, применить миграции, сравнить `drizzle-kit introspect`). Справочные данные — только в `seed`, не в миграциях.

### 4.7. Домен «очередь» перегружен [карта]

В §0: «очереди 1/2/3». В Приложении B: «`1` — свет есть, `3` — отключение, `2` — переходное состояние» (это коды **состояний** интервала). И при этом очередь называется «2/2», «1/1…6/2» (подочереди). Слово «черга/очередь» означает и идентификатор группы потребителей, и код состояния. Плюс три синонима: ГПВ, ГАВ, «заходи обмеження».

**Решение:** словарь терминов в коде и API: `queue` (группа потребителей, строка `"2.2"`), `slotState` (`on | off | maybe`), `regime` (тип ограничения). Не использовать `/` в идентификаторе (§5.4).

### 5.2. Безопасность API

- **Rate limit 100 req/min на IP** [карта]. Если браузер ходит на API **через nginx-прокси** (`location /api/`), то для Fastify все запросы приходят с IP контейнера nginx. Без `trustProxy: true` и проброса `X-Forwarded-For`/`X-Real-IP` лимит **общий на всех пользователей сразу**. **[проверить]** `trustProxy` в `server.ts` и заголовки в `nginx.conf`. Это потенциально «сайт ложится от 100 запросов в минуту суммарно».
- CORS `origin: '*'` вместе с тем, что `VITE_API_BASE_URL=http://localhost:3001/api/v1` (§9) — браузер ходит на API напрямую; для прода нужен относительный путь `/api/v1` и закрытый CORS (список доменов).
- `helmet` на JSON-API малополезен; а **на nginx со статикой заголовков безопасности нет** (CSP, `X-Content-Type-Options`, `Referrer-Policy`) **[проверить]**.
- Статический `ADMIN_TOKEN`: нет ротации, нет логирования действий (кто/когда менял `street_queues`), нет раздельных прав.

### 5.3. Парсинг и источники

- **Основной источник — закрытый эндпоинт оператора** (`POST /api/list_acc`, тип 1/2/6), который вы повторяете «WAF-friendly» (`requestDelayMs`, `sessionWarmup`). Любое изменение на стороне оператора ломает продукт без предупреждения, а доступ защищён WAF, который уже блокировал ваш IP (§13.7).
- Карта предлагает «выждать бан или парсить с другого IP». **Обход блокировки — плохая стратегия**: это юридический и репутационный риск, и она не масштабируется. **[вывод]** Правильнее: ограничить частоту, ставить кэш/условные запросы, и **связаться с оператором** (Чернігівобленерго) насчёт официального источника/открытых данных. Для проекта «для жителей одного села» шанс договориться реалистичный. **Обновлено 2026-10-10:** дозвіл отримано — обхід і account-ендпоінти дозволені (див. `AGENTS.md`).
- **Telegram-парсинг** (`TelegramChannelAdapter` — посты канала, `TELEGRAM_RULES`) — парсинг HTML публичной веб-версии, хрупкий; бот выключен. Для оповещений бот/каналы полезнее как **канал доставки**, а не только как источник.
- `chernihiv.adapter.ts` (HTML-вариант) и `chernihiv-web.adapter.ts` — два адаптера на один сайт. **[проверить]** жив ли старый.
- `mock.adapter.ts` и `USE_MOCK_ADAPTER` — для dev хорошо; убедиться, что в проде невозможно включить случайно (отдельный профиль).
- Сырые снапшоты (`rawSnapshotRef`) и `snapshots/` внутри контейнера **[проверить]**: в compose нет volume под них → теряются при пересоздании контейнера; одновременно в них могут быть ПД (§3.5).
- Нет **схем валидации ответа оператора** (zod на выходе адаптера) **[проверить]**: при смене формата `parseListAccRow` должен падать громко с понятной ошибкой, а не писать мусор.
- Нет **backoff/circuit breaker**: повторные запросы при бане усугубляют бан.

### 5.4. Геокодинг

В бэкенде был `geocode.service` — фейк-заглушка: Nominatim не вызывался, возвращались фиксированные координаты (51.4938/31.2953), файл никто не импортировал; удалён 2026-10-10. Осталась одна система — фронтовая `resolveOutageMapPoint`: **таблица координат городов области + дефолт**. На карте отключений точки поставлены по грубой таблице, не по реальным адресам. Для села с ~20 улицами это означает «все отключения в одной точке».

**Решение:** либо честно писать «примерное положение» и не рисовать улицы, либо хранить координаты улиц в `addresses` (20 улиц геокодируются один раз и вручную проверяются). Не держать две системы.

### 5.5. Время

Три реализации «киевских суток»: `lib/outage-dates.ts` (web), `power-summary.ts`/`reliability.ts` (api), SQL `at time zone`. Плюс `kyivWallClockToUtc` и `schedule-normalizer`. Все описаны как корректные, но это **четыре места, где можно ошибиться при смене DST**.

**Решение:** один пакет `packages/shared/time` (на `luxon` или `Temporal`), тесты на даты перехода (последнее воскресенье марта/октября) — один раз, для всех.

### 5.6. Окружение и сборка

- `packages/shared` «без сборки, потребляется как исходники», а API запускается как `node dist/server.js` [карта]. Рантайм Node не умеет исполнять `.ts` внутри `node_modules`; значит, как-то это обходится (symlink workspace, флаги, бандл) **[проверить как именно]** — хрупкая конструкция. **Решение:** собирать `shared` в `dist` обычным `tsc` и ссылаться на `main`/`exports` → `dist`.
- `moduleResolution: Bundler` в API [карта], при том что код исполняется **напрямую в Node ESM** (`node dist/server.js`). Bundler-режим не требует расширений и не проверяет, что Node сможет разрешить импорт; правильный режим для Node — `NodeNext`.
- Хост: node 26 / pnpm 11; образы: node 22 / pnpm 9.15 [карта]. Node 26 — **не LTS** (нечётная ветка). Версия lockfile pnpm 11 может не читаться pnpm 9.15 с `--frozen-lockfile` **[проверить]**. **Решение:** `engines` и `packageManager` в корневом `package.json`, `.nvmrc`/`.node-version` = 22 (или 24 LTS), разрабатывать на той же версии, что и в образе.
- `uuid-ossp` в `init.sql` — в PG13+ есть встроенный `gen_random_uuid()`, расширение лишнее (P3). И `init.sql` выполняется **только при первой инициализации тома** — расширения, созданные там, не появятся на уже существующем томе **[вывод]**; а `unaccent` создаётся где-то в миграциях. Расширения — только в миграции `0000_extensions`.

## 7. Инфраструктура, эксплуатация, безопасность

### 7.1. Состояние рантайма

`api — Exited (137)`, `web — Exited (1)`, `db — Exited (0)` [карта]. Код 137 — SIGKILL (OOM-killer или `docker kill`/остановка хоста). `web` с кодом 1 — **гипотеза [проверить]**: nginx не стартует, если `proxy_pass http://api:3001` указывает на имя, которое в момент старта не резолвится (api остановлен) — классический `host not found in upstream`. Лечится `resolver 127.0.0.11 valid=10s;` + `set $upstream http://api:3001;` + `proxy_pass $upstream;`, либо `depends_on: api: condition: service_healthy`.

Первым шагом: `docker compose logs --tail=200 api web` и `docker inspect <id> --format '{{.State.OOMKilled}}'`.

### 7.2. Compose

- **[проверить]** `restart: unless-stopped` — в карте не упоминается, а контейнеры «остановлены». Без политики после перезагрузки хоста продукт не поднимется.
- У `api` нет `healthcheck`, `web` зависит от `api` только по факту старта.
- `x-api-env` «жёстко перекрывает `.env`» [карта]. Для прод-настроек правильнее: `.env` — единственный источник значений, compose содержит только структуру. Сейчас правка `.env` у `ENABLE_SCHEDULER` ничего не изменит — это ловушка, о которой знаешь только по карте.
- Нет лимитов памяти/CPU; при OOM (137) это уместно.
- Сервис `migrate` использует `image: svitlo-api:latest`, а `api` собирается по `build:`. **[проверить]** что имя образа и тег гарантированно совпадают, иначе `migrate` запустит старый образ без новых миграций.
- Контейнер API **[проверить]** запускается от root? Добавить `USER node`.
- Нет `volume` для логов/снапшотов (см. §5.3).

### 7.3. Бэкапы и восстановление

Только том `pg_data`. Нет `pg_dump` по расписанию, нет проверки восстановления. Данные воспроизводимы (оператор, Telegram), но **`street_queues`, `schedule_slots` (ручной импорт), `contacts`** — ручной труд. Минимум: ночной `pg_dump` в отдельное хранилище + документированная команда восстановления.

### 7.4. Эксплуатационная наблюдаемость

- Логи pino — хорошо, но нет метрик и алертов.
- Когда оператор забанит IP (§13.7), узнаете от пользователей. Нужен алерт: «нет успешного парса > 2 ч» (в `/status` уже есть `dataStale`, подключите внешний пинг: UptimeRobot/healthchecks.io на `/ready`, возвращающий 503 при `dataStale`).
- `parse_runs` — отличная таблица для этого; к ней нужен просто «дашборд» из одного SQL.

### 7.5. CI

Обязательного CI нет [карта]. «Линт» = `tsc --noEmit` (ESLint нет). Чек-лист «Перед коммитом» написан руками в §14 — переносим в GitHub Actions: `pnpm i --frozen-lockfile` → `tsc` → `vitest` → `vite build` → `docker build`. ## 9. Продукт и домен

1. **Название и охват расходятся.** «Svitlo — Чернігів» и «жителей Черниговской обл.», а реально: один `CHERNIHIV_CITY_IDS=7422288601` (с. Деснянське), ~20 курируемых улиц, график — одна очередь `2/2` в `useMyQueues`. Решите, чем продукт является: **(A)** «Деснянське» — тогда упрощайте; **(B)** область — тогда нужен справочник населённых пунктов и улиц, а не курируемый сид.
2. **Если (A)**: стек (Fastify + PG + Drizzle + nginx + PWA + рейт-лимит + 10 роутеров) тяжеловат для пары улиц и нескольких событий в неделю. Реалистичный упрощённый вариант: один контейнер (Fastify + SQLite/Postgres), поиск улиц — **загрузить все ~20 улиц на клиент и искать локально** (fuse.js), без `pg_trgm`, `energy_normalize_address`, `unaccent`, `address-matcher`, `/addresses/suggest`. Поиск «шел» → «Шевченка» заработает/не заработает по вашему порогу, зато мгновенный и офлайн.
3. **«Надійність» (`reliabilityPct`)** — доля времени со светом по опубликованным оператором отключениям. Внеплановые отключения, которых оператор не публиковал, не учитываются. **[вывод]** Показатель называть «за повідомленнями оператора», иначе он вводит в заблуждение и может подставить вас в споре с кем-то.
4. **Самая полезная для жителей функция — уведомления** («у вашей очереди отключение через 30 минут»). В проекте нет ни Web Push, ни Telegram-уведомлений — при том что Telegram-бот-адаптер есть (выключен). Это главная точка роста продукта после того, как данные заработают.
5. **ГПВ вручную** (userscript → браузер → `POST /admin/schedules/import` с токеном) — зависимость от человека, делающего это ежедневно. Если ГПВ — главный «график» для жителей, без автоматизации продукт мёртв. Пути: официальный источник у оператора; парсинг публикации графика (если публичная страница/картинка); подписка на их Telegram-канал с разбором графика; или честно сказать, что график ведётся вручную, и дать ответственному человеку удобный путь (Telegram-бот `/import`).
6. **Юридическое**: что оператор разрешает по ToS при автоматизированном доступе; что вы храните (ПД, §3.5); указание источника данных и дисклеймер «не является официальным».

## 11. Неточности и странности в самой карте

Карта отличная, но стоит поправить:

1. «Всё проверено по коду» (§0) — не верифицируемо без git и CI; стоит писать дату и хеш коммита после `git init`.
2. «Однострочные минифицированные файлы — норма» (§8.4) — не норма (§6.1).
3. «Поиск „шел“ не находит „Шевченка“ — это свойство реализации» (§12.7). Тут **опечатка в самом запросе**: «шел» — это не префикс «шев». Пример `curl` в §10 использует `q=шев` — он корректный. Фраза вводит в заблуждение: настоящий вопрос — «нужна ли терпимость к опечаткам» (см. §9.2 — для 20 улиц решается клиентским fuzzy).
4. В §6 сказано, что расширение `unaccent` часть стека, а `init.sql` создаёт только `uuid-ossp` и `pg_trgm` — где создаётся `unaccent`, не сказано.
5. В §8.5 сказано, что токены мапятся, а в §13 в `AddressCombobox` оставлены обходные inline-цвета «чтобы не зависеть от отсутствующих токенов» — токены уже не «отсутствующие»; противоречие.
6. «Линт» в §10 — это `tsc`, при этом §14 пишет «ошибки в node_modules — игнорировать»; значит `tsc` ходит и в `node_modules` — это конфигурационная ошибка.
7. «`dataStale` = нет обновления > 2 ч» при `PARSE_INTERVAL_MINUTES=30` и выключенном планировщике — состояние «stale» штатное, а не аварийное; карта не описывает, чем оно отличается от реального сбоя.

## 12. С чего начать: план переделки

Оценки ориентировочные для одного разработчика, знакомого с кодом.

### Этап 0 — «Остановить кровотечение» (0,5 дня)

1. Архив `cp -r` → `git init` → `.gitignore` → первый коммит → приватный remote.
2. Удалить `/tmp/*` с токенами/счетами. Сменить `ADMIN_TOKEN` и пароль БД.
3. Закрыть порт `5432` наружу.
4. Удалить `generate-frontend.js`, `nohup.out`, `.turbo/`.
5. `docker compose logs` и `docker inspect` — понять причины `137` и `Exit 1`.
6. Проверить, не светится ли что-то в публичном доступе (если сервер был виден из интернета).

### Этап 1 — «Сделать продукт живым» (1–2 дня)

1. `ENABLE_SCHEDULER=true`, `SCHEDULE_DEMO=false` в прод-конфиге; убрать жёсткий оверрайд в `x-api-env` (значения из `.env`).
2. HTTPS (Caddy перед nginx — 10 строк конфига) и относительный `VITE_API_BASE_URL=/api/v1`.
3. `restart: unless-stopped`, healthcheck api, `resolver` в nginx (§7.1).
4. `trustProxy` + корректный rate-limit (§5.2).
5. Внешний пинг на `/ready` (503 при `dataStale`).
6. Админку убрать из публичной навигации; закрыть на уровне nginx.
7. Блок «Мій графік» без демо — честный EmptyState.

### Этап 2 — «Починить ядро данных» (3–5 дней) — **главная работа**

1. Таблицы `outage_events` + `outage_addresses`, миграция данных из `outages` (скрипт, с бэкапом).
2. Дедуп и **категория** — на ингесте; столбец `category`; удаление `outageCategory` на фронте.
3. Статус — вычисляемый; `updateOutageStatuses` убрать.
4. `/outages`, `/status`, `/reliability`, `/outages/stats` читают одну модель; пагинация в SQL.
5. Интеграционный тест «цифры совпадают» (§8) — **сначала** написать (он упадёт: 30 ≠ 6), потом чинить.
6. Таймлайн: строка = событие (`event.id`).

### Этап 3 — «Автоматизировать график» (по ситуации: 1–2 дня + переговоры)

1. Определить официальный/устойчивый источник ГПВ.
2. Идентификатор очереди без `/`; одна ручка расписания.
3. Если источник — вручную: Telegram-бот/CLI для импорта вместо веб-админки.

### Этап 4 — «Подчистить фронтенд» (2–3 дня)

1. Prettier + ESLint; удалить дубли (§6.3); единый клиент; единый `NAV_ITEMS`.
2. Tailwind-токены: убрать inline-хаки, тест на неизвестные токены; проверить «Контакти».
3. Ленивая загрузка карты и графиков, анализ размера бандла.
4. i18n: убрать хардкод или оставить один язык.
5. Тесты на таймлайн, `QueueScheduleBar`, `AddressCombobox`, хуки.

### Этап 5 — «Процесс» (1 день)

GitHub Actions (tsc → lint → vitest → build → docker build), Dependabot, `pg_dump` по расписанию, README.

### Этап 6 — «Продуктовое» (когда этапы 0–3 закрыты)

Решение A/B (§9.1); уведомления (Web Push / Telegram); дисклеймер и источник данных; запрос официального доступа у оператора.

## 14. Чего делать НЕ надо

- **Не переписывать всё с нуля.** Чистая логика и парсеры стоят дороже, чем кажется.
- Не менять `energy_normalize_address()` без новой миграции и пересчёта `name_normalized` (карта права).
